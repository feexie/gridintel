# ADR 0012: Build every screen ahead of time when the dataset cannot change

Date: 2026-10-07
Status: **Proposed. Not implemented. The Founder decides.**

## Context

The hosted preview runs on Vercel and is public (ROADMAP, hosting notes).
Vercel runs the app in function instances that it starts on demand and
discards when idle. Each new instance generates the synthetic dataset and
computes the screens again, and until it has, a visitor is shown "Preparing
data". On 2026-10-07 every data screen of the live site answered with that
page, and `/api/ready` reported `warming` for several minutes through more
than 300 requests: an instance appears to be suspended between requests, so
work started at start-up and not tied to a request barely advances.

The warm-up was designed for one long-lived Node process, where it runs once
and takes about 6 s. That is still the right design for such a host. It is
the wrong one for a host with no long-lived process, and the Founder has
ruled out patching it.

What makes another answer possible is a property of the demonstration
adapter, already written down in `src/composition/runtime.ts`: the dataset
is generated by code and never changes, and "now" is a fixed demo clock.
Every screen is therefore the same on every request, for as long as the
build is. A screen that cannot change does not need a server to compute it.

## Proposal

1. **A fixed dataset is a stated property of an adapter, not a test for
   "demo".** The composition root exposes one fact, for example
   `datasetIsFixed()`: true when the running adapter's records cannot change
   and its clock does not move. The synthetic demo adapter says true. An
   adapter over a database, an API or telemetry says false. Nothing else in
   the application asks which adapter is running.
2. **When the dataset is fixed, every screen is rendered at build time**
   and served as a file. Each dynamic route gets `generateStaticParams`,
   which asks the composition root for the ids of its level (regions,
   substations, feeders, transformers, service points) and returns them
   when the dataset is fixed and an empty list when it is not.
3. **When the dataset is not fixed, the path is the one that exists today.**
   A page first asks the composition root whether the dataset is fixed; when
   it is not, it calls `connection()` (the Next.js 16 way to say "wait for a
   request"), so nothing is rendered at build time and each request is
   answered from the result cache, with the warm-up, the preparing page and
   `/api/ready` exactly as now. The `export const dynamic = "force-dynamic"`
   on Reliability and Revenue is replaced by that call, because a segment
   option is a literal and cannot depend on the adapter.
4. **Three screens choose a longer list by query string** (`?feeders=all` on
   Executive, `?valuation=all` on Revenue, `?rows=all` on a transformer). A
   page built ahead of time cannot read a query string. Each becomes a path
   of its own (for example `/revenue/all`), and the old address redirects to
   it. The screens themselves do not change.
5. **The data-truth rules are unchanged.** The view models, the services and
   the components are the same; only when a screen is rendered moves. The
   SYNTHETIC DATA bar is in the layout and is in every built page. The
   "Data as of" time in the bar is the demo clock, as now, so a built page
   does not claim to be fresher than it is.

## Page count and build time

Counted from the registry and measured on the development laptop on
2026-10-07, production build, unless marked as an estimate.

| Kind of screen | Pages | HTML each |
| --- | --- | --- |
| Already built ahead of time (overview, hub, Operations home, placeholders) | 15 | small |
| Executive, Reliability, Revenue, with the two longer-list variants | 5 | 0.2 to 0.6 MB |
| Assets, Events / Alarms (6c-3) | 2 or more | not measured |
| Region, substations, feeders | 7 | 0.36 to 0.46 MB |
| Transformers, short and full list | 96 | 0.45 and 0.9 MB |
| **Network screens in all** | **about 125** | |
| Service points | **6,448** | 0.05 MB |

- **Computing.** The network screens take about 6 s (today's warm-up).
  Computing all 6,448 service-point view models took 20 s in one process.
- **Rendering and writing** (estimate, not measured): Next.js renders pages
  in several worker processes, each of which generates the dataset (0.4 s)
  and holds its own results (about 300 to 400 MB each). The network screens
  should add well under a minute to the build. The service points should
  add a few minutes.
- **Output size** (from the measured page sizes): about 60 MB for the
  network screens; about 490 MB for the service points, counting each
  page's HTML and its navigation payload (49 KB and 27 KB).

Two ways to treat the service points, for the Founder to choose between:

| | A. Build all 6,448 | B. Build the network screens; a service point on first visit |
| --- | --- | --- |
| Build | Several minutes longer, about 0.5 GB of output | Under a minute longer, about 60 MB |
| A visitor's first look at a service point | A file, at once | Rendered once by a function, then kept as a file. The function generates the dataset (0.4 s) and computes one view; there is no warm-up to wait for |
| "Preparing data" | Never shown on the fixed dataset | Never shown on the fixed dataset |
| Risk | Whether Vercel's build limits accept it is not checked; it must be tried on a preview before it is relied on | A function is still involved for service points, so its memory (about 300 MB) and the plan's limits still apply |

**Recommendation: B.** It removes the cold start from every screen a visitor
reaches first, at a small build cost, and leaves A open: A is B with one
list returned from `generateStaticParams`.

## What `/api/ready` and the preparing page become

- **On a fixed dataset** there is no warm-up: `register()` in
  `src/instrumentation.ts` does not start one, readiness stays
  `not_started`, and `/api/ready` answers 200 with that state, which is what
  it already answers for a process with no warm-up. `isPreparing()` is never
  true, so the preparing page is never rendered. Both stay in the code,
  because the dynamic path needs them.
- **On any other adapter** both behave exactly as today.
- `/api/ready` stays a statement about one process. The hosting notes
  already say it is not a health signal for a Vercel deployment.

## Effect on the browser tests

- **Most tests do not change.** They read what a screen shows, and the
  screens are the same. They would run faster: the 16 routes of the timing
  test are files.
- **`global-setup.ts`** still waits for `/api/ready` and still passes; on a
  fixed dataset it passes at once.
- **`readiness.spec.ts` would fail as written**: it starts a server and
  expects the preparing page first. The dynamic path must stay tested, so
  the proposal needs a way to run it on purpose: an environment variable
  read only by the composition root (for example
  `GRIDINTEL_RENDER=request`) that makes it report the dataset as not
  fixed. `verify` would then build twice, or the readiness test would run
  against a second build made with that variable. That lengthens `verify`
  and is the main cost of this proposal on the engineering side.
- **`timing.spec.ts`** would measure file serving for the built screens. The
  500 ms budget is about the engine; it should be kept on the dynamic build
  as well, or it stops testing anything.
- **Tests that follow the three "show all" links** change their expected
  addresses from a query string to a path.
- **A new test**: on the fixed build, a data screen answers with its figures
  on the first request to a server that has just started, with no preparing
  page.

## Consequences

- A public visitor never sees "Preparing data" on the demonstration.
- A change to the dataset or the engine reaches the site only through a new
  build. That is already true: the dataset is code.
- The build needs the memory to generate the dataset and compute the screens
  (about 300 to 400 MB per worker).
- The composition root gains one question (`datasetIsFixed`) and the pages
  one call. No layer boundary moves.
- When a real adapter arrives, nothing here has to be undone: it answers
  false and takes the dynamic path.

## Not proposed

Changing the warm-up; adding a cache service or a database; a paid Vercel
feature; changing what any screen shows.

## Decisions asked of the Founder

1. Adopt the proposal, or not.
2. Service points: A or B.
3. Accept a longer `verify` so that both paths stay tested.
